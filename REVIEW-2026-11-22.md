## 1. What the project is

A Power BI dashboard of weekly card spending at points of sale (shop card machines) in Riyadh and other Saudi cities. The figures come from the weekly PDF reports that SAMA (the Saudi Central Bank) publishes.

How it fits together:

| Part | What it does |
|---|---|
| `scripts/update.py` | The weekly job. It finds new SAMA PDFs on SAMA's website, downloads them, extracts the numbers, checks them and writes the CSVs. |
| `scripts/extract_pos.py` | Reads the text out of a SAMA PDF and turns its tables into rows: activities (Table 1) and cities (Tables 2.1–2.2). |
| `scripts/checks.py` | Sanity checks. Totals must add up, no week can be missing, no city can appear or disappear, and no week-on-week swing can be absurd. If any check fails, nothing is written. |
| `data/activities.csv`, `data/cities.csv` | The cleaned data: 61 weeks, from week ending 20 Sep 2025 to week ending 14 Nov 2026. |
| `.github/workflows/update.yml` | GitHub runs the tests, tries SAMA Tuesday to Friday, and emails you if the data goes more than 21 days stale. |
| `scripts/run_weekly.ps1` | Does the same update from your PC. This is needed because SAMA only answers Saudi internet connections. |
| `RiyadhSpending.pbip` + `RiyadhSpending.SemanticModel/` + `RiyadhSpending.Report/` | The Power BI project. It reads the CSVs straight from GitHub, builds a weekly Date table and has 38 DAX measures over 3 pages. |
| `tests/test_pipeline.py` | 12 automated tests. They check that the committed data passes every check, that the checks catch broken data, and that new reports are found on SAMA's page. |

What I checked: I read every script, the workflow, the tests, the README, all the semantic-model (TMDL) files and the filters on the report pages. I ran the test suite (all pass). I also re-calculated the reconciliation figures, the Riyadh share and Riyadh vs Jeddah, the average payments and the top-10 cities from the CSVs myself.

## 2. Bugs and likely bugs

### 2.1 The reconciliation checks are already at their limit (likely to cause a false failure soon) — HIGH
**Where:** `scripts/checks.py:10-11`

**What goes wrong:** SAMA prints figures rounded to the nearest SAR 1,000, so the parts never add up exactly to the printed total. The checks allow a small gap. I measured the biggest gap in the 61 weeks of real data:

| Check | Allowed | Largest seen so far |
|---|---|---|
| 61 cities vs Total (value) | 6,000 | **6,000** (at the limit) |
| 27 activity lines vs Total (value) | 6,000 | 4,000 |
| Subtotal vs its parts (value) | 1,000 | **1,000** (at the limit) |
| Subtotal vs its parts (transactions) | 2,000 | **2,000** (at the limit) |

Rounding 61 city figures can in theory produce a gap of up to about 30,000. The Transportation subtotal has 6 parts, so its gap can reach about 3,500. A week that is perfectly fine could therefore fail the check. The weekly update would then refuse to write it, and the data would go stale until someone loosens the limit by hand.

**Suggested fix:** base each limit on how many rows are added together. For example, allow 1,000 × √(number of rows) × 3, or simply 1,000 × number of rows ÷ 2 (the maximum possible rounding error). That gives about 30,000 for cities, 14,000 for activity lines and 1,000 × (parts + 1) for each subtotal. These are still tiny next to a weekly total of about SAR 13 billion, and they would still catch a misread number, which is normally off by millions.

### 2.2 The Task Scheduler command in the README is broken — HIGH (quick win)
**Where:** `README.md:79-81`

**What goes wrong:** *(corrected while fixing)* the command line itself is complete. Under it, though, the code block had two stray lines (`iyadh-card-spending\scripts` and `un_weekly.ps1\""`), left over from a `\r` that was turned into a line break when the README was written. Pasting the whole block runs those junk lines as well and shows errors, which makes it look as if the setup failed. The task itself is most likely fine, but it's worth checking in Task Scheduler that it exists and points at your real path (`E:\Claude Projects\riyadh-card-spending\scripts\run_weekly.ps1`).

**Fix:** delete the two stray lines.

### 2.3 A failed package install on the PC is never retried — MEDIUM
**Where:** `scripts/run_weekly.ps1:18-22`

**What goes wrong:** the script only installs the Python packages when the `.venv` folder does not exist yet. If the first install fails halfway (say the internet drops), `.venv\Scripts\python.exe` still exists. Every later run then skips the install and fails with "No module named pdfplumber". A change to `requirements.txt` is also never picked up.

**Suggested fix:** run `& $py -m pip install --quiet -r scripts\requirements.txt` on every run, outside the `if`. It takes a second when nothing has changed. Also check `$LASTEXITCODE` after `python -m venv` and after `pip install`.

### 2.4 A failed push on the PC is not retried until new data arrives — MEDIUM
**Where:** `scripts/run_weekly.ps1:27-36`

**What goes wrong:** if `git commit` succeeds but `git push` fails (network blip), the commit sits on your PC. Next week the script sees "no data changes" (the change is already committed) and never pushes it. GitHub, and Power BI, which reads from GitHub, keep showing the old week until a newer report arrives. Separately, if GitHub Actions ever commits data itself, `git pull --ff-only` fails on the PC and the PC job stops working until someone fixes it by hand.

**Suggested fix:** after the commit block, always run `git push` when the local branch is ahead of `origin/main`. Check with `git status -sb` or `git rev-list --count origin/main..HEAD`. For the second case, use `git pull --rebase` instead of `--ff-only`, since the PC only ever changes `data/`.

### 2.5 The PC job could commit other files you had staged — LOW
**Where:** `scripts/run_weekly.ps1:27-33`

**What goes wrong:** it stages `data/`, but `git diff --cached` and `git commit` act on everything staged. If you had staged some other edit by hand, it would go out in the "Data through week ending …" commit.

**Suggested fix:** commit only the data with `git commit -m "..." -- data/`.

### 2.6 `update.py` crashes if `data/cities.csv` is missing or empty — LOW
**Where:** `scripts/update.py:140-141`

**What goes wrong:** when there is no existing data, `after` is `None`, and `after + dt.timedelta(days=7)` and `weeks[-1] <= after` raise a `TypeError`. The code elsewhere tries to handle `after is None` (lines 135, 173), so this was meant to work. Today it doesn't matter, because the data exists. It would bite on a fresh rebuild.

**Suggested fix:** at the top of the loop's stop condition, add `if after is None: continue`, so the loop keeps everything up to the download limit. Or document that a fresh start must use `extract_pos.py` instead.

### 2.7 Page-order detection can miss when the first two reports have the same date — LOW
**Where:** `scripts/update.py:137-139`

**What goes wrong:** the script guesses whether SAMA's page lists reports oldest-first by comparing the first two reports it opens. If those two cover the same week (for example the same report linked twice under different names), it never reverses. On an oldest-first page it then downloads from the oldest end up to the 25-file limit. It may not reach the new report, and the run says "nothing new" when there is something new.

**Suggested fix:** decide the order from the first two *different* week dates. Simpler still: download, read the week dates of every link up to the limit, and keep the ones after `after`.

### 2.8 When there is a gap, the update downloads 25 files before giving up — LOW
**Where:** `scripts/update.py:140-142`

**What goes wrong:** if the new reports don't reach back to the week after your newest data (you missed more than about 4 weeks), `covered` can never become true. The loop keeps downloading older reports it will ignore, until it hits `MAX_DOWNLOADS`. The checks then correctly fail with "Gap". The result is right, but slow, and the message doesn't say what to do.

**Suggested fix:** stop as soon as a report older than `after` is seen, and print a clear message: "new reports start on X but data ends on Y: download the missing report(s) by hand and run `update.py --pdf …`".

### 2.9 A test name promises more than it checks — LOW (quick win)
**Where:** `tests/test_pipeline.py:30-33`

`test_data_starts_on_first_week_and_is_recent` only checks there are at least 56 weeks, not that the data is recent. Freshness is already covered by `--stale-after` in the workflow, so either rename the test or drop "and_is_recent".

### 2.10 Files opened without being closed — LOW
**Where:** `scripts/update.py:83`, `scripts/extract_pos.py:135,138`, `tests/test_pipeline.py:16`

`open(...)` is passed straight to `csv.DictReader` and never closed. CPython usually closes these straight away, so it works today. Even so, `extract_pos.py` reads `data/*.csv` and then rewrites the same files, and on Windows a still-open file can block that. Use `with open(...) as f:`.

## 3. Security and privacy

Overall: **no real problems found.**

- **Secrets:** none in the repo. The only credential mentioned is GitHub's built-in `github.token` in the workflow, which is the right way to do it. `.venv/`, the downloaded PDFs and the PC log are kept out of git by `.gitignore`.
- **Personal or financial data:** the data is published aggregate statistics (city and sector totals), with no individuals in it. The only personal detail in the repo is your GitHub username and its GitHub "noreply" email, used as the commit author. That is normal for a public repo and does not expose your real email.
- **Workflow input:** the manual "pdf_url" input is passed through an environment variable rather than pasted into the shell command. That is the safe pattern and avoids command injection. Only people with write access to the repo can start a manual run.
- **Downloads:** files come over HTTPS from sama.gov.sa, at most 25 per run, and are recognised by their contents before use. pdfplumber reads the PDFs without running anything in them. Risk is low.
- **Small hardening ideas (optional):**
  - In `.github/workflows/update.yml:52`, `$PDF_URL` is used unquoted, so a value containing `*` would be expanded by the shell. Only repo writers can set it, so this is cosmetic. Splitting with `read -ra urls <<< "$PDF_URL"` and passing `"${urls[@]}"` would be tidier.
  - Pin the GitHub Actions to commit hashes instead of `@v5`/`@v6` if you want to be strict about supply-chain risk.
- **Power BI:** it reads the CSVs from the public raw GitHub URL with "Anonymous" sign-in. That is fine for public data. It does mean the dashboard depends on the repo staying public.

## 4. Data correctness

What I verified directly from the CSVs:

- 61 weeks in both files, every one a Saturday, 7 days apart, no gaps (20 Sep 2025 → 14 Nov 2026).
- 31 activity rows (27 lines + 3 subtotals + Total) and 61 city rows every week, the same names every week.
- Riyadh = 34.5% of Kingdom card spending over the whole period, and 2.53 × Jeddah. The average payment is SAR 62.7 in Riyadh and SAR 69.4 in Jeddah. These match the README's findings (34%, 2.5×, SAR 63 vs 70). The README figures were for the first 56 weeks, so tiny differences are expected.
- Week-on-week change in the total ranges from −18% to +38%, well inside the −50%/+100% guard.
- The "Restaurants & Cafés" accent is stored correctly (UTF-8) in both the data and the report's filter, so that line chart filter works.
- The "Week Type" rule (a week ending on day 1–7 contains the 1st of the month) is correct for Sunday–Saturday weeks.
- The 2025–26 holiday dates in the Date table look right: Ramadan from 21 Feb to 14 Mar 2026, Eid al-Fitr on 21 Mar, Eid al-Adha on 30 May, and National Day on 27 Sep 2025 and 26 Sep 2026.

Issues:

### 4.1 Holiday labels end in 2026 — MEDIUM (time-sensitive)
**Where:** `RiyadhSpending.SemanticModel/definition/tables/Date.tmdl:235-239`

Ramadan 1448 starts around 8 Feb 2027. Without new dates, the Ramadan and Eid 2027 weeks will be coloured as "Regular week" in the page 1 and page 3 charts. The README already flags this, but nothing reminds you when it is due.

**Fix:** add the 2027 dates now (Ramadan, Eid al-Fitr, Eid al-Adha, National Day 23 Sep 2027, which falls in the week ending Sat 25 Sep 2027). Better still, move the holiday dates into a small `data/holidays.csv` that the Date table joins to, so a year can be added without touching the model. Optionally add Founding Day (22 Feb).

### 4.2 Revised figures replace old ones silently — LOW
**Where:** `scripts/extract_pos.py:144-159`

When SAMA revises a past week, the newest report wins. That is the right rule, but nothing records what changed. A large revision, or a parsing slip in one report that still passes the checks, would overwrite good data without anyone noticing.

**Fix:** in `update.py`, before writing, compare the overlapping weeks with what is already in `data/` and print any row that changed by more than, say, 1%. Optionally fail on changes above 10%.

### 4.3 A few city names are slightly wrong — LOW (cosmetic)
**Where:** `scripts/extract_pos.py:93-98` (how wrapped names are joined)

When a city name wraps onto two lines in the PDF, the two parts are glued together with no space and no hyphen. In the data this produced "Hafrel-Batin" (should be "Hafr Al-Batin"), "Wadil-Dawaser" ("Wadi Al-Dawaser") and "Al-laith" ("Al-Laith"). The numbers are fine; only the labels look odd in Power BI.

**Fix:** keep a small "display name" lookup in `extract_pos.py` that maps the parsed name to the proper one. Changing the names in the CSVs means the change also has to be made in any report filter that uses them; none of these three is used in a filter today.

### 4.4 The "ten biggest cities" list on page 2 is typed in — LOW
**Where:** `RiyadhSpending.Report/report.json` (visual filters `vf_top10a`, `vf_top10b`)

The bar chart and table use a fixed list of 10 cities, while the subtitle (`Sub P2` in `_Measures.tmdl:373`) says "the ten biggest cities by card spending". The list is still correct today, for both the whole period and the latest week, with Makkah and Al-Madinah swapping places in the latest week. It won't update itself if the ranking changes.

**Fix:** use a Top N filter (Top 10 by `City Spend`, excluding "Others") instead of a fixed list, or reword the subtitle to "ten of the biggest cities".

### 4.5 Smaller notes (no action needed unless you use these features)
- `'Spend WoW %'` and `'Sector WoW %'` compare the whole selected period with the single week before the last one. They are right only when one week is in context. The report only uses the "Latest …" versions, which are correct, so this matters only if someone drops the raw measure into a new visual.
- `'Month'` in the Date table is the month of the week-ending Saturday, so a week spanning two months counts fully in the later month. Monthly totals built from it are approximate. No current visual uses it.
- `strptime("%d %b %y")` in `extract_pos.py:62` depends on the computer's language settings. It works on English Windows and on GitHub. On a PC set to Arabic it could fail to read the dates, and `update.py` would then treat every PDF as "not a POS report".
- Average payment uses transaction counts rounded to thousands. For the smallest city (about 215,000 transactions a week) the error is under 0.25%, which is negligible.
